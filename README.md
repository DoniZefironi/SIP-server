# Телефония SAVT

Сервис на Python (FastAPI) рядом со станцией Asterisk. Слушает события станции, складывает их
в базу и отдаёт по HTTP. Меню, очереди и запись делает сам Asterisk; если сервис остановлен,
звонки идут как обычно.

Полное описание задачи — в [telephony-service-brief.md](telephony-service-brief.md).

## Что уже есть

- Подключение к станции по AMI (поток событий Asterisk, TCP-порт 5038) с переподключением при обрыве.
- Настройки станции в [asterisk/](asterisk/): сценарий, очереди, SIP, AMI и гайд по применению.
- Таблица `call_events`: события звонков (новый канал, вызов, ответ, очередь, отбой)
  и этапы сценария станции (`SavtCall`, `SavtRecording`, `SavtMessage`).
- `GET /health` — состояние сервиса, базы и связи со станцией (200 или 503).
- `GET /api/events?limit=50&linkedid=…` — последние события, для отладки.
- Журнал звонков: `GET /api/calls` (фильтры `sector`, `outcome`, `caller`, `date_from`, `date_to`),
  `GET /api/calls/{id}`, записи `GET /api/calls/{id}/audio/{mix|client|staff|message}`.
- Очередь `recording_jobs`: готовый WAV разговора или голосового сообщения завершённого звонка
  ставится в очередь один раз, в том числе если файл появился после отбоя. Проверка проходит
  при запуске и затем каждые 15 секунд, пока включена `TELEPHONY_RECORDING_QUEUE_ENABLED`.
- Асинхронное распознавание через Yandex SpeechKit. `GET /api/calls/{id}` отдаёт статус и текст.
  Для разговора с двумя доступными дорожками текст содержит реплики клиента и сотрудника с временем.
  Голосовые сообщения и записи с одной дорожкой сохраняются обычным текстом.
  Для запуска задать `TELEPHONY_SPEECHKIT_ENABLED=true` и `TELEPHONY_SPEECHKIT_API_KEY` в `.env`.
  После включения сервис отправляет WAV до 60 МБ из очереди, включая накопленные задачи.
  Если SpeechKit мог принять файл, но идентификатор операции не сохранился, задача переходит
  в `failed`, чтобы избежать автоматической повторной загрузки.
- Выжимка через YandexGPT на основе сохранённой расшифровки. `GET /api/calls/{id}` отдаёт
  её статус, суть обращения, договорённости, следующие действия и однозначно распознанный код
  сделки. Для запуска задать `TELEPHONY_YANDEXGPT_ENABLED=true`, `TELEPHONY_YANDEXGPT_FOLDER_ID`
  и `TELEPHONY_YANDEXGPT_API_KEY` в `.env`. Обрабатываются и накопленные расшифровки.
- Доставка выжимок в Bitrix24 через входящий вебхук с правами `crm` и `im`.
  В личном сообщении сотруднику указывается имя со ссылкой на карточку звонящего
  либо номер, если CRM-карточка не найдена.
  `GET /api/calls/{id}` показывает адресатов, статус каждой отправки и ID записи в Bitrix24.
  Перед включением `TELEPHONY_BITRIX_ENABLED` заполнить `TELEPHONY_BITRIX_WEBHOOK_URL`
  и назначить резервных получателей по секторам при необходимости. При включении обрабатываются
  и накопленные выжимки. Если факт отправки после таймаута не удалось подтвердить по истории,
  доставка получает статус `uncertain` для ручной сверки.
- Обслуживание раз в час: удаление пустых записей, записей старше года
  (`TELEPHONY_RECORDINGS_RETENTION_DAYS`) и сырых событий старше 90 дней.
- Приведение номеров к виду `+375291234567`.

API слушает только на самой машине. При подключении фронтенда прокси проверяет доступ
к панели и права администратора на изменение настроек отделов.

## Устройство

```
app/
  main.py          запуск сервиса и фоновой задачи AMI
  config.py        настройки из переменных окружения (TELEPHONY_*)
  ami/client.py    клиент AMI
  ami/events.py    какие события сохраняем
  api/             HTTP-эндпоинты
  db/              модели и подключение к PostgreSQL
  services/        журнал звонков, номера, обслуживание
alembic/           миграции базы
tests/             тесты (станция в них поддельная, Asterisk не нужен)
```

## Стенд для фронтенда

Из корня репозитория с Python 3.13, uv и Docker запустить:

```sh
docker compose -f compose.frontend.yml up -d --wait
uv run --locked python -m scripts.frontend_demo
```

API будет доступен на `http://127.0.0.1:18081`, Swagger на [/docs](http://127.0.0.1:18081/docs),
контракт на [/openapi.json](http://127.0.0.1:18081/openapi.json). Стенд использует отдельную
базу на порту `15432`, выполняет миграции и заполняет её тестовыми звонками. Внешние
интеграции отключены. Данные остаются между запусками и сохраняют те же ID.

| Карточка | Что проверить |
| --- | --- |
| `1` | Разговор, общая и две отдельные WAV-дорожки, диалог с таймкодами, выжимка и доставка в Bitrix24 |
| `2` | Голосовое сообщение и обычный текст расшифровки |
| `3` | Звонок завершился в очереди, запись отсутствует |
| `4` | Расшифровка в обработке |
| `5` | Расшифровка завершилась ошибкой |
| `6` | Звонок ещё идёт |
| `7` | Исходящий звонок с записью и инициатором |

В WAV используются короткие тоны для проверки загрузки и перемотки. Тексты, выжимки
и статусы доставки заданы как примеры. `GET /health` для стенда возвращает `ami: "disabled"`.

### Подключение интерфейса

- `GET /api/calls?limit=50&offset=0` отдаёт `{ items, total }`. Фильтры `sector`, `outcome`,
  `caller`, `date_from` и `date_to` применяются на сервере. `date_from` включается в диапазон,
  `date_to` исключается. Передавать даты в ISO 8601 с часовым поясом.
- Для вкладок истории передавать `tab=incoming` для принятых входящих, `tab=outgoing`
  для исходящих сотрудника, `tab=missed` для завершённых входящих без ответа. Во вкладке
  пропущенных `voicemail=true` выбирает звонки с голосовым сообщением, `voicemail=false`
  выбирает звонки без сообщения. Для вкладки «Все» внутри пропущенных опустить `voicemail`.
- `GET /api/calls/counts` возвращает `incoming`, `outgoing`, `missed`,
  `missed_with_voicemail` и `missed_without_voicemail`. Передавать те же `date_from`, `date_to`,
  `sector` и `caller`, что в списке. Счётчики считаются по всему диапазону.
- Для колонки «Отдел» использовать `sector_name` и `sector_number`. Номера задаются
  через `TELEPHONY_SECTOR_NUMBERS`, например `{"4":"+375..."}`. Для колонки «Сотрудник»
  использовать `employee_name`, затем `initiated_by` или `answered_by`.
  Сопоставление с именами задаётся через `TELEPHONY_EMPLOYEE_NAMES`. У исходящих поле
  `caller` содержит номер клиента, которому позвонили.
- `voicemail_left` фиксирует факт записи голосового сообщения после регистрации
  готового WAV очередью обработки. `has_message` показывает, доступен ли файл сейчас.
- `GET /api/calls/{id}` отдаёт поля звонка, расшифровку, выжимку и список доставок
  в Bitrix24 с отдельным статусом по каждому адресату. Активный звонок определяется по
  `ended_at: null`. Поля обработки могут быть `null`, пока задача ещё не создана.
- `GET /api/calls/{id}/audio/{kind}` отдаёт `audio/wav`. `kind` принимает `mix`, `client`,
  `staff` или `message`. Для `mix` и `message` используются флаги `has_recording` и
  `has_message`. Для отдельных дорожек обработать `404`. Через прокси передать `Range` и
  `If-Range` на API и сохранить статус и заголовки `Accept-Ranges`, `Content-Range`,
  `Content-Type` и `Content-Length` в ответе.

Во фронтенде использовать относительные URL через прокси на том же домене. При
локальной разработке адрес API для прокси — `http://127.0.0.1:18081`. Для API на ВМ можно
открыть SSH-туннель на компьютере, где запущен прокси:

```sh
ssh -N -L 18080:127.0.0.1:8000 siptrunk@10.1.0.148
```

С этим туннелем адрес API для прокси — `http://127.0.0.1:18080`. Для доступа сотрудников
прокси должен применять авторизацию приложения к журналу и WAV.

Остановка стенда — `Ctrl+C` в окне API, затем `docker compose -f compose.frontend.yml down`.

### Статистика

Оба отчёта принимают `date_from`, `date_to` и необязательный `sector`. Границы задаются
в ISO 8601 с часовым поясом. Начало периода включается, конец исключается.

- `GET /api/statistics/calls` отдаёт итоги в `totals` и данные графика в `buckets`.
  `group_by` принимает `day`, `week` или `month`. По умолчанию используется `day`.
  `bucket_start` — дата начала календарного интервала по Минску. Неделя начинается
  в понедельник. Для интервалов без звонков фронт ставит нули. `total` — сумма
  `incoming`, `outgoing` и `missed`. Для пропущенных есть разбивка
  `missed_with_voicemail` и `missed_without_voicemail`.
- `GET /api/statistics/callers` возвращает `{ items, total }`. Каждая строка содержит
  номер клиента `caller`, количество входящих `calls`, количество пропущенных
  из них `missed` и время последнего вызова `last_called_at`. Строки идут от самых
  частых номеров к самым редким, при равных значениях сверху идут недавние.
  Для пагинации используются `limit` и `offset`. В отчёт попадают звонки
  с распознанным номером, принятые сотрудником или завершённые без ответа.

### Отделы

- `GET /api/departments` отдаёт дерево отделов плоским списком `items` с `parent_id`,
  количеством сотрудников, настройками маршрута и состоянием звонков. Поле `sectors`
  содержит номера секторов Asterisk для выбора в настройках.
- `GET /api/departments/{id}` добавляет список `employees` с именами, должностями и фото.
  Справочник Bitrix24 обновляется при запросах с кэшем на 60 секунд. `directory_present: false`
  означает, что в Asterisk осталась привязка к отделу, исчезнувшему из справочника.
- `PUT /api/departments/{id}/settings` сохраняет маршрут. Пример тела запроса
  `{"sector":4,"primary_number":"+375291234567","additional_numbers":[],"busy_mode":"queue","queue_wait_seconds":120}`.
  Основной номер используется для дозвона. Дополнительный можно назначить основным
  в этом же редакторе. Режим `message` переключает звонок на голосовое сообщение после дозвона,
  `queue` использует очередь. `queue_wait_seconds: null` берёт общий таймаут станции.
  Занятый другим отделом сектор даёт `409`.
- `DELETE /api/departments/{id}/settings` снимает привязку и возвращает `204`. Сектор
  снова работает с настройками AstDB, заданными для него до привязки отдела.
- `call_status` принимает `in_call`, `idle`, `unconfigured` или `unknown`.
  `active_calls` показывает число активных разговоров, когда статус известен. При
  `settings_available: false` справочник доступен, а сохранение привязки недоступно.

Для запуска установите `TELEPHONY_BITRIX_DIRECTORY_ENABLED=true` и добавьте вебхуку из
`TELEPHONY_BITRIX_WEBHOOK_URL` права `department` и `user_brief`. Маршрут в карточке
хранится по ID отдела в AstDB. Для чтения и записи маршрутов [настройте AMI](asterisk/GUIDE.md#7-доступ-для-сервиса-телефонии-ami)
и загрузите обновлённый `extensions.conf`. Вызов основного номера отдела пойдёт через PJSIP-транк,
указанный в `outbound_trunk`. До подключения транка Asterisk использует телефон сектора из
`sector_N_target` или тестовый `PJSIP/10N`.

## Запуск на рабочем компьютере (без Asterisk)

Нужны Python 3.13, uv и Docker.

```
copy .env.example .env
```

В `.env` задать `TELEPHONY_DB_PASSWORD` и поставить `TELEPHONY_AMI_ENABLED=false`. Затем:

```
uv sync
docker compose up -d db
uv run alembic upgrade head
uv run uvicorn app.main:app --reload
```

Проверка: открыть http://127.0.0.1:8000/health и http://127.0.0.1:8000/docs.

Тесты и проверка кода:

```
uv run pytest
uv run ruff check .
```

## Запуск на сервере (ВМ siptrunk)

На ВМ проверены тестовые звонки через PJSIP, запись и API. Проверка входящих с внешней
линии потребуется после подключения SIP-транка.

Для исходящих звонков через Asterisk см. [настройку SIP-учётных записей сотрудников](asterisk/GUIDE.md#исходящие-звонки-сотрудников).

**1. Станция.** Сначала применить настройки Asterisk по [asterisk/GUIDE.md](asterisk/GUIDE.md):
там же скачивается репозиторий в `/opt/savt-telephony` и создаётся пользователь AMI `telephony`
(пароль — в `/root/ami-secret.txt`).

**2. Сервис.**

```
cd /opt/savt-telephony
sudo cp .env.example .env
sudo cat /root/ami-secret.txt
sudo nano .env
```

В `.env` задать:
- `TELEPHONY_DB_PASSWORD` — свой случайный пароль, например из `openssl rand -hex 16`;
- `TELEPHONY_AMI_SECRET` — пароль, который показала команда `sudo cat /root/ami-secret.txt`;
- `TELEPHONY_ASTERISK_GID` — число из команды `getent group asterisk | cut -d: -f3`
  (сервис входит в группу `asterisk`, чтобы читать и чистить записи в `/srv/recordings`).

Запуск:

```
sudo docker compose up -d --build
```

Команда собирает образ, поднимает базу, создаёт таблицы и запускает сервис. Проверка:

```
curl http://127.0.0.1:8000/health
```

Ожидаемый ответ: `{"status":"ok","db":"ok","ami":"connected"}`. После тестового звонка
`curl http://127.0.0.1:8000/api/events` покажет его события.

Сервис слушает только `127.0.0.1:8000`, база — только `127.0.0.1:5432`. Наружу ничего не открыто.
