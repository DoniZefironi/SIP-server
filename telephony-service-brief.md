# Телефония SAVT: ТЗ-контекст для агента, пишущего сервис на Python

Документ собран 16.11.2026 из обсуждения с владельцем проекта. Он самодостаточный: переписки нет,
всё нужное здесь. Пометки:

- **Решено** — решил владелец проекта, менять без него нельзя.
- **Предложение** — предложено в обсуждении, владелец не отклонил или не рассматривал. Можно оспорить.
- **Проверено** — реально проверялось (где именно, указано).
- **Не проверено** — не проверялось, считать гипотезой.

## 1. Задача

Компания SAVT (производство шкафов управления, Беларусь) делает телефонную линию для клиентов.
Клиент звонит на единый номер, попадает в голосовое меню, выбирает сектор (отдел), звонок уходит
на телефон сектора. Вне рабочего времени клиент оставляет голосовое сообщение.

Нужно написать **сервис на Python** (отдельный репозиторий), который расширяет станцию Asterisk:
определение звонящего, обработка сообщений, журнал звонков, настройки, голосовой бот.
Меню, очереди и переадресация уже сделаны штатными средствами Asterisk (см. раздел 6), Python для
них не нужен.

## 2. Что решено (владелец)

- Оператор: **life:** (Беларусь). Договор ещё **не подписан**. Линия — SIP, привязанный к SIM-карте;
  ограничение «одна SIM — один разговор» к ней не относится. Один единый номер вида `+37525…`,
  «10 виртуальных номеров» = **10 одновременных каналов**.
- Доступ к серверу life: только через мобильную сеть SIM, поэтому нужен LTE-роутер **TP-Link** с этой SIM.
  Авторизация регистрацией (IP сервера регистрации и исходящего прокси, логин и пароль выдаст life:).
- Своя станция **Asterisk** на виртуальной машине в офисе. Готовую виртуальную АТС оператора не берём.
- Телефония живёт **в отдельном репозитории**, не в `savtAssistApp-server`. Данные о звонящем и базу
  знаний для бота сервис берёт у бэкенда SavtAssist по API.
- Asterisk, сервис на Python и фронт — на одной ВМ в офисе.
- Сектора (названия тестовые, пока так): **1 Сервис, 2 Коммерческий, 3 Производство, 4 Бухгалтерия,
  5 Снабжение**. У каждого сектора **один рабочий телефон**, и это **обычный мобильный номер**
  (звонок на него станция делает второй ногой через life:, занимая два канала из десяти).
  В будущем возможно подключение Bitrix24 (не проверялось, детали не обсуждались).
- Рабочее время: **пн–пт 8:00–17:00**, часовой пояс Минск.
- Если телефон сектора занят или не отвечает: клиент слышит «вы первый в очереди» и музыку.
  Очередь на сектор **до 2 ожидающих**, время ожидания по умолчанию **не ограничено**.
  Третьему и следующим предлагаем оставить сообщение.
- Меню: неверная цифра или тишина → сообщение и повтор меню, **3 попытки**, потом клиент идёт
  в сектор **Коммерческий** (по умолчанию).
- Вне рабочего времени (и при переполненной очереди): клиент оставляет **сообщение**
  («назовите имя, номер и суть вопроса, мы перезвоним»). Позже на это место встанет **бот**,
  который отвечает и записывает, что хотел клиент.
- Приветствие и фразы озвучивает **голос сотрудника** (записи будут). В приветствии есть
  предупреждение о записи разговора.
- Прямой набор внутреннего номера из меню **не нужен**.
- Минимум на сейчас: меню, очереди, переадресация, сообщения. Без админки, распознавания и бота
  на первом этапе.

## 4. Схема

```
 Клиент ── телефонная сеть ──> [ SIP-сервер life: ]
                                      │ (сеть life:, вход только с их SIM)
                               [ Роутер TP-Link + SIM ]
                                      │ (офисная сеть)
                        ┌──────[ Asterisk (на хосте ВМ) ]──────┐
                        │            │                          │
              телефоны секторов   [ Сервис телефонии ]       записи и сообщения
              (мобильные, через   (Python, Docker)           /srv/recordings
               линию life:)            │
                    ┌──────────────────┼──────────────────┐
             [ Бэкенд SavtAssist ]  [ Яндекс ]        [ Bitrix ]
              кто звонит, проект,   распознавание,     комментарий в сделку
              база знаний для бота  выжимка, голос
```

Сервис управляет звонками через **ARI** (HTTP + WebSocket, порт 8088 Asterisk). Asterisk стоит
прямо на хосте ВМ, не в контейнере. Всё остальное (сервис, база, фронт) предполагается в Docker.

## 5. Как идёт звонок (целевое поведение, уже заложено в настройках Asterisk)

1. Клиент звонит на единый номер, звонок приходит от life: на наш Asterisk, попадает в `[from-trunk]`
   и далее в `[reception]`.
2. Станция снимает трубку (с этого момента занят канал). Проверяет время: пн–пт 8:00–16:59 по Минску.
3. **Рабочее время:** играет меню (`menu`), ждёт цифру 1–5 (6 секунд). Неверная цифра → `wrong`,
   тишина → `nochoice`, меню повторяется; после трёх неудач → сектор по умолчанию (`DEFAULT_SECTOR=2`).
4. Клиент в очереди сектора (`q1`…`q5`). Станция звонит на телефон сектора 20 секунд, пробует снова
   каждые 3 секунды. Занято или не ответили: после первой неудачной попытки клиент слышит `qfirst`
   («все специалисты заняты, вы первый в очереди») и `qthanks` («оставайтесь на линии»), потом музыка;
   фраза повторяется раз в 60 секунд. Второй ожидающий слышит музыку.
   Третий ожидающий (очередь `maxlen=2`) → `queuefull` → сообщение.
5. **Вне рабочего времени:** фраза `afterhours`, затем запись сообщения.
6. **Запись сообщения:** сигнал, до 120 секунд, остановка после 5 секунд тишины, файл
   `/srv/recordings/messages/ГГГГММДД-ЧЧММСС-НОМЕР.wav` (`unknown`, если номер скрыт; номер
   очищен до цифр), затем `thanks` и завершение.
7. Звонок на телефон сектора идёт через контекст `[sector-phone]` по переменным `SECTOR_1…SECTOR_5`.
   Сейчас там внутренние SIP-номера `PJSIP/101…105` (тест). После договора — мобильные через линию:
   `PJSIP/+375…@life-trunk` (формат номера определит life:).

Фразы (файлы wav 8 кГц моно 16 бит) лежат в `/var/lib/asterisk/phrases/` (пока это тестовые тоны):
`menu`, `wrong`, `nochoice`, `afterhours`, `queuefull`, `thanks`, `qfirst`, `qthanks`.
Полные файлы настроек — в приложении А.

## 6. Что должен делать сервис на Python

Меню, очереди, часы работы и запись сообщений **делает Asterisk сам** и должны оставаться
работоспособными, даже если сервис упал. Сервис нужен там, где звонком надо управлять из кода.

**Правило отказоустойчивости (обязательное).** Любой переход звонка в сервис (приложение Stasis через
ARI) делается так, чтобы при недоступном сервисе звонок продолжал идти по обычному сценарию
Asterisk. Нельзя, чтобы падение сервиса обрывало звонки.

Предлагаемые этапы (**предложение**, порядок согласовать с владельцем):

1. **Каркас.** Подключение к ARI (WebSocket), проверка состояния, журнал, конфигурация из окружения,
   Docker-образ. Без влияния на звонки.
2. **Журнал звонков.** Кто звонил, в какой сектор, кто ответил, длительность, итог (отвечен,
   пропущен, сообщение). Источник: события ARI или CDR Asterisk.
3. **Определение звонящего.** По номеру спросить у бэкенда SavtAssist, кто это (контакты проектов
   приходят туда из Bitrix). Неопознанный звонок — не ошибка. Результат попадает в журнал и
   показывается сотруднику.
4. **Обработка сообщений.** Забирать файлы из `/srv/recordings/messages/`, распознавать
   (Yandex SpeechKit), делать краткую выжимку (YandexGPT), сохранять в журнал, при опознанном
   звонящем писать комментарий в сделку Bitrix. SpeechKit и YandexGPT уже подключены в бэкенде.
5. **Запись разговоров.** Запись на диск `/srv/recordings`, срок хранения не решён.
6. **Рабочее время и настройка меню и секторов из админки** (сейчас они зашиты в `extensions.conf`
   и `queues.conf`). Админка — существующая React/Next.js.
7. **Голосовой бот** (ответ первым и вне рабочего времени), ответы из базы знаний через API бэкенда,
   перевод на человека, если не справился.
8. **Фронт телефонии:** журнал звонков (кто звонил, кто ответил, запись, текст, выжимка).

На первом этапе (по решению владельца) бота, распознавания и админки **нет**; задача сервиса —
каркас, журнал и определение звонящего.

## 8. Размещение, сеть, безопасность

Порты ВМ (в интернет не публикуется **ничего**; сотрудники вне офиса — через VPN):

| Порт | Откуда | Зачем |
|---|---|---|
| 22 TCP | офисная сеть `10.1.0.0/24` (и адреса админов) | SSH |
| 5060 UDP | офисная сеть, VPN, адреса life: | SIP |
| 10000–10199 UDP | офисная сеть, VPN, адреса life: | голос |
| 443 TCP | офисная сеть, VPN | фронт и API сервиса |
| 9090 TCP | офисная сеть | Cockpit |

Правила для адресов life: добавятся после договора (их IP неизвестны). Порты ARI (8088) и базы (5432)
доступны только внутри машины.

**Технические замечания, которые влияют на код и Docker:**

- **ARI и Docker.** Asterisk на хосте, ARI по умолчанию слушает `127.0.0.1`. Контейнер до него не
  дотянется. Нужно либо `network_mode: host` у сервиса, либо привязать ARI к адресу моста Docker
  и ограничить доступ. Выбор не сделан. Потребуется пользователь ARI в `ari.conf` и настройка
  `http.conf`.
- **Docker обходит `ufw`.** Опубликованные порты контейнеров остаются открытыми независимо от
  правил `ufw`. Порты базы и внутренних сервисов публиковать только на `127.0.0.1`.
- **PostgreSQL.** В исходном списке стоит «PostgreSQL 16», но в Ubuntu 26.04 в репозитории версия
  выше. Проще и устойчивее держать базу в контейнере (в исходном описании база названа в составе
  Docker-части). Решение не принято.
- Установка Docker и nginx пока не выполнялась; хост минимальный намеренно (меньше поверхность атаки).
- Время на ВМ `Europe/Minsk`, `chrony` синхронизирует. Все метки времени в сервисе хранить в UTC,
  отображать по Минску.
- Расход места: ~1 МБ на минуту WAV (8 кГц, 16 бит, моно), около 0,2 МБ сжатого. Если писать обе
  стороны раздельно (стерео), объём удваивается. Срок хранения записей и ответственный за диск —
  не решены.

## 9. Ограничения и риски

- **10 каналов life:.** Разговор с сектором по мобильному занимает **два** канала (клиент +
  исходящая нога), то есть одновременно максимум 5 таких разговоров. Ожидающие в очереди тоже
  занимают канал. Когда все 10 заняты, следующий клиент получает от оператора «занято».
- **Мобильный телефон сектора.** Станция не видит, занят ли мобильный: она просто звонит и получает
  «занято» или «не ответили». Голосовая почта оператора на такой SIM **должна быть отключена**,
  иначе станция примет автоответчик за ответившего человека. Звонок на мобильный ограничен ~20 секундами.
- **Всё, что касается life:, не проверено:** регистрация через NAT роутера, адреса в SDP
  (нужны `external_media_address`/`external_signaling_address`/`local_net`, если роутер делает NAT),
  способ передачи DTMF (на линии стоит `rfc4733`, лучше `auto`, пока life: не ответила),
  отключён ли SIP ALG на конкретной модели TP-Link, можно ли с линии звонить на мобильные и какой
  номер увидит вызываемый.
- **Единая точка отказа:** ВМ, роутер, LTE и интернет офиса. Запасного пути нет (вопрос к life:
  про переадресацию при недоступности станции открыт). Нужен мониторинг: оповещение, если
  регистрация перестала быть `Registered`.
- **Запись разговоров и персональные данные.** В приветствии есть предупреждение о записи.
  Отправка записей в Яндекс — передача персональных данных за границу, это стоит обсудить с юристом
  до включения распознавания.
- Музыка ожидания: только с лицензией на такое использование. Сейчас играет стандартная музыка
  Asterisk (`musicclass=default`).

## 10. Открытые вопросы

**К life: (после договора или вместе с ним):**
1. IP и порт сервера регистрации, IP и порт исходящего прокси.
2. Транспорт: UDP, TCP или TLS.
3. Логин, имя для авторизации, пароль, домен (realm). Регистрация одна на 10 каналов или на каждый?
4. Рекомендуемый интервал перерегистрации.
5. Кодеки и их порядок (G.711 alaw/ulaw, G.729, другие).
6. Способ передачи DTMF: RFC 2833, SIP INFO или в голосовом канале.
7. Формат номера звонящего и формат номера для исходящего вызова (`+375…`, `375…`, `80…`).
8. Можно ли звонить с линии на мобильные и городские, какой номер увидит вызываемый
   (хотелось бы номер клиента).
9. Модель роутера TP-Link, что на нём настраивает life:, какой адрес получит наш сервер,
   нужен ли проброс портов, NAT или маршрутизация, отключён ли SIP ALG.
10. Диапазон адресов, с которых приходят сигнализация и голос.
11. Есть ли переадресация на другой номер, если наша станция недоступна.
12. Допускает ли договор собственный Asterisk на этой линии; 10 каналов на одной SIM-регистрации.
    Тестовое подключение до оплаты.

**Внутренние:**
- Какие реальные номера секторов (мобильные) и кто в каком секторе.
- Сколько одновременных звонков в пик.
- Срок хранения записей и сообщений, кто отвечает за место на диске.
- Как фронт телефонии ходит за данными: напрямую в сервис или через бэкенд SavtAssist.
- Какие служебные эндпоинты нужны в бэкенде (поиск звонящего по номеру, база знаний для бота)
  и как они защищены.
- Выбор между `network_mode: host` и привязкой ARI к мосту Docker.
- Статический адрес ВМ (`10.1.0.148`): закреплён ли.

- Гайды для сервера: **полные последовательности команд от входа по SSH, с конкретными значениями**,
  без шаблонов в угловых скобках. Каждую команду объяснять простыми словами.
- Термины объяснять простыми словами. Язык общения — русский.
- Гайды и спецификации отдавать текстом или файлом, не ссылкой на опубликованную страницу.

## 12. Словарь

- **SIP** — протокол, по которому телефоны и станции договариваются о звонке.
- **Asterisk** — программа-станция: принимает звонки и решает, что с ними делать.
- **Транк (линия)** — подключение станции к оператору.
- **Регистрация** — вход станции или телефона на сервер с логином и паролем.
- **Кодек** — способ сжатия голоса. Самый распространённый — G.711 (alaw, ulaw).
- **DTMF** — передача нажатий цифр во время звонка; нужна для меню.
- **PJSIP** — модуль Asterisk для SIP; файлы `pjsip*.conf`.
- **Диалплан** — сценарий звонков; файл `extensions.conf`.
- **ARI** — интерфейс, через который программа на Python управляет звонками в Asterisk
  (HTTP + WebSocket); приложение на стороне Asterisk называется Stasis.
- **SIP ALG** — функция роутера, которая вмешивается в SIP и обычно ломает звук; отключается.
- **Очередь** — механизм Asterisk (`Queue`): держит клиентов, пока телефон сектора не освободится.

### queues.conf

```
[general]
persistentmembers=no

[sector-defaults](!)
strategy=ringall
timeout=25
retry=3
wrapuptime=3
ringinuse=no
maxlen=3
joinempty=yes
leavewhenempty=no
announce-frequency=60
announce-holdtime=no
announce-position=limit
announce-position-limit=1
queue-youarenext=/var/lib/asterisk/phrases/qfirst
queue-thankyou=/var/lib/asterisk/phrases/qthanks
musicclass=default

[q1](sector-defaults)
member => Local/1@sector-phone/n

[q2](sector-defaults)
member => Local/2@sector-phone/n

[q3](sector-defaults)
member => Local/3@sector-phone/n

[q4](sector-defaults)
member => Local/4@sector-phone/n

[q5](sector-defaults)
member => Local/5@sector-phone/n
```

Пояснения к настройкам:

- Каждый сектор — очередь `qN` с одним участником `Local/N@sector-phone/n`. Адрес телефона сектора
  хранится в одном месте, в `[globals]` (`SECTOR_N`), и меняется одной строкой.
- `Background()` вместо `WaitExten()` выбран намеренно: при `WaitExten` ветка `t` (тишина) не срабатывала,
  если после него есть другие строки в расширении.
- Шаблон `_[+0-9].` в `[from-trunk]` ловит номера с «+» и без, не срабатывая на служебные события
  (`h`, `i`, `t`). `_.` использовать нельзя.
- Файлы фраз указаны полным путём (`/var/lib/asterisk/phrases/…`): у пакета Ubuntu папка звуков
  устроена нестандартно (`custom` — ссылка на `/usr/local/share/asterisk/sounds`).
- Своя фраза очереди `qfirst` и `qthanks` подменяют английские `queue-youarenext` и `queue-thankyou`;
  без подмены клиент услышит английский голос.

## Приложение Б. Что надо знать о тестовых телефонах

Пять SIP-номеров 101–105 (пароли случайные, создаются скриптом) временно играют роль телефонов
секторов, чтобы проверить сценарий до договора. Приложение на телефоне: Zoiper, Linphone (Android,
iOS) или MicroSIP (Windows); аккаунт: логин `101`…`105`, сервер `10.1.0.148`, транспорт UDP.
Эхо-тест: набрать `600`. Вход «как клиент»: набрать `700` с внутреннего номера.

Линия life: в `pjsip_trunk.conf` ещё не настроена. Заготовка схемы «регистрация + исходящий прокси»
(PJSIP: объекты `registration`, `auth`, `aor`, `endpoint`, `identify`, `outbound_proxy` с `\;lr`)
не проверялась на линии life: и будет уточняться по их ответам.

## Приложение В. Что именно проверялось на тестовой копии

Asterisk 20.6 (Ubuntu 24.04), звонки имитировались каналами Local:

1. Конфигурация загружается без ошибок: пять очередей, пять SIP-номеров, диалплан.
2. Занятый сектор: клиент ждёт, участник очереди показан как «In use», второй звонок на сектор
   не звонит параллельно (`ringinuse=no`).
3. Очередь продвигается: когда сектор освобождается, соединяется следующий.
4. Лимит: при 3 ожидающих четвёртый получает `QUEUESTATUS=FULL`, играет `queuefull`, уходит в запись сообщения.
5. Сектор не отвечает: 20 секунд звонка, повтор через 3 секунды, `qfirst` + `qthanks` после первого цикла.
6. Меню: неверная цифра → `wrong`; тишина → `nochoice`; три неудачи → сектор по умолчанию.
7. Вне рабочего времени (проверено сдвигом окна `GotoIfTime`): `afterhours` → запись сообщения.
8. Запись сообщения: файл создаётся с датой и номером в имени.
9. Файлы wav, сделанные `ffmpeg` (`-ar 8000 -ac 1 -c:a pcm_s16le`), воспроизводятся.

**Не проверялось** (см. разделы 3 и 9): живые телефоны, линия life:, Asterisk 22.5, ARI и Python-сервис.
